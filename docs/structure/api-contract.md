# EnergyTool AI — API Contract

**Версия:** `1.0.0-draft`  
**Статус:** предварительный контракт MVP  
**Период разработки:** 9–16 ноября 2026 года  
**Команда:** Frontend Developer · Backend Developer · AI/ML Engineer

> **Назначение документа.** Единый контракт запросов и ответов для независимой разработки Frontend, Business Backend и AI Service. Примеры имён, контактов, идентификаторов, рекомендаций и временных меток — демонстрационные. Упомянутые ID продуктов необходимо сверить с утверждённым каталогом EnergyTool.

## 1. Архитектура и границы ответственности

```text
                   Public HTTP API                   Internal HTTP API
[Frontend] <----------------------> [Business Backend] <------------------> [AI Service]
                                               |
                                               | SQL / ORM
                                               v
                                       [Central Database]
```

- **Frontend (React/TypeScript):** отображает чат, историю, карточки решений, форму заявки и панель менеджера. Работает только с **Public API**.
- **Business Backend (FastAPI):** единственный владелец доступа к пользовательской БД. Создаёт и проверяет сессии, хранит историю, профиль клиента и заявки, обращается к AI Service, возвращает ответы Frontend.
- **AI Service (FastAPI):** **не хранит пользовательскую историю**. На каждом запросе получает текущее сообщение и предыдущую историю, формирует контекст, использует продуктовую базу знаний / RAG (при необходимости), вызывает LLM и возвращает структурированный результат.
- **Database:** одно централизованное хранилище данных приложения. Для MVP допустим SQLite (один Backend-процесс), при наличии опыта команды — PostgreSQL.
- **Product Knowledge Base:** проверенный каталог решений EnergyTool. Может находиться в `data/products.json` и использоваться AI Service для поиска, а Backend — для проверки ID и сборки публичных карточек.

**Не входит в первый MVP:** кэш истории, WebSocket/стриминг, брокер сообщений, сложная агентная система, реальная CRM-интеграция без требования ТЗ.

## 2. Общие соглашения

### 2.1. Протокол и сериализация

- Формат тела HTTP-запросов и ответов: `application/json; charset=utf-8` (кроме запросов без тела).
- Путь Public API начинается с `/api/` и доступен браузеру через Backend.
- Путь Internal API начинается с `/v1/` и доступен **только** Business Backend по внутренней сети/сервисной аутентификации.
- Временные метки: ISO 8601, рекомендуется UTC (`2026-11-09T12:30:00Z`).
- Идентификаторы: строки. Примеры `session-123` и `request-456` условны; в реализации предпочтительны случайные UUID.
- Поля, не известные на текущий момент: `null`, а не выдуманные значения.
- `product_ids`: только идентификаторы из утверждённого каталога; не генерировать произвольные ID.
- `history` всегда содержит **только предыдущие** сообщения, отсортированные по возрастанию времени/порядкового номера. Текущее сообщение присутствует отдельно в `message` и **не дублируется** в `history`.
- В `history` для AI передаются завершённые сообщения пользователя и ассистента. Сообщение со статусом `pending` в историю как завершённый диалог не включается.

### 2.2. Идемпотентность запросов

- Frontend присваивает каждой новой отправке сообщения `request_id` (уникальный в пределах сессии). При сетевом повторе того же сообщения использует **тот же** `request_id`.
- Backend обеспечивает уникальность пары `(session_id, request_id)`; повтор обработанного запроса возвращает прежний результат без второго вызова LLM, повтор незавершённого — `409 Conflict`.
- Для создания заявки Frontend передаёт `submission_id`; повтор с тем же `(session_id, submission_id)` не должен создавать новую заявку.
- Backend не допускает конкурентной обработки двух новых сообщений одной сессии. Для MVP достаточно проверки статуса активного запроса на стороне Backend (плюс блокировки ввода во Frontend для удобства).

### 2.3. Доступ и безопасность

- `session_id` — идентификатор данных, **не** доказательство права доступа. Для анонимного чата рекомендуется защищённая `HttpOnly` cookie, связанная с сессией на сервере. Если Frontend сохраняет `session_id` в `localStorage`, это **не** заменяет проверку доступа на Backend.
- Маршруты `/api/admin/*` доступны только авторизованному менеджеру. Для MVP допускается простой демонстрационный механизм аутентификации, но не публичный просмотр контактов.
- AI Service не вызывается напрямую из браузера и не получает телефон/email клиента без необходимости.
- LLM/API-ключи хранятся только в переменных окружения серверных компонентов; не включаются в репозиторий и ответы API.
- Перед сохранением контактов проверяются согласие пользователя и данные для обратной связи; журналы не должны раскрывать ключи и избыточные персональные данные.
- Не предоставлять универсальные API для выполнения произвольных SQL-запросов (`/api/db/{table}/query`). Запросы к БД выполняются Backend через ограниченные сервисы/репозитории.

## 3. Справочные типы данных

### 3.1. `Action`

*— перечисление допустимых действий ИИ-консультанта. Определяет тип ответа модели и дальнейшее поведение интерфейса: уточнение информации, ответ на вопрос, рекомендация продукта, предложение консультации с менеджером или обработка запроса вне компетенци*

Ровно одно из значений:

| Значение | Семантика | Что делает Frontend |
|---|---|---|
| `answer_question` | Ответ на вопрос клиента | Показывает текст |
| `ask_question` | Уточнение потребностей | Показывает вопрос |
| `recommend` | Рекомендация одного или нескольких продуктов | Показывает текст и карточки продуктов |
| `offer_handoff` | Предложение консультации менеджера | Предлагает форму контактов (пользователь может отказаться) |
| `out_of_scope` | Запрос вне компетенции или недостаточно достоверных данных | Показывает текст с ограничением |

`Action` — **метка следующего диалогового действия**, не команда на создание заявки. Реальная заявка создаётся **только** через `POST /api/leads` после явного подтверждения пользователя.

### 3.2. `HistoryMessage`

*— базовая структура сообщения в истории диалога. Содержит роль отправителя (user или assistant) и текст сообщения (content). Используется при передаче истории диалога из Backend в AI-сервис для формирования контекста LLM.*

```json
{
  "role": "user",
  "content": "У нас 50 магазинов"
}
```

- `role`: `"user" | "assistant"` — обязательно.
- `content`: непустая строка — обязательно.

### 3.3. `CustomerProfile`

*— структурированный профиль клиента, содержащий сведения о его бизнесе, потребностях и инфраструктуре. Формируется и обновляется AI-сервисом в ходе диалога, сохраняется Backend в БД и используется для подбора продуктов и формирования заявок.*

```json
{
  "business_type": "retail",
  "objects_count": 50,
  "problem": "Высокие расходы на электроэнергию",
  "metering_method": "manual"
}
```

Все четыре ключа **всегда присутствуют**. Значение любого ключа может быть `null`. Для MVP достаточно следующих полей:

| Поле | Тип | Значение |
|---|---|---|
| `business_type` | `string \| null` | Тип организации, например `retail` |
| `objects_count` | `integer \| null` | Число объектов клиента (целое положительное) |
| `problem` | `string \| null` | Основная задача / проблема клиента |
| `metering_method` | `string \| null` | Способ учёта, например `manual` или `automatic` |

Backend хранит последнюю проверенную версию профиля. AI Service возвращает **полный снимок** профиля, а не только новые поля. Backend не должен автоматически затирать известный факт значением `null` без обоснования; при противоречиях следует сохранить исходные сообщения и при необходимости запросить уточнение.

### 3.4. `ProductCard`

*— структура представления продукта EnergyTool. Содержит идентификатор, название и краткое описание решения. Формируется Backend на основании рекомендованных AI-сервисом идентификаторов продуктов и используется Frontend для отображения рекомендаций.*

```json
{
  "id": "cloud_askue",
  "name": "Облачная АСКУЭ",
  "description": "Автоматизированный сбор и обработка показаний приборов учёта."
}
```

ID `cloud_askue` — **условный пример**, должен совпадать с каталогом. AI Service возвращает только `product_ids`; Backend формирует полные карточки продуктов из утверждённого каталога.

### 3.5. `ChatMessage`

*— расширенная структура сообщения диалога. Помимо роли отправителя и текста, содержит уникальный идентификатор сообщения и время его создания. Используется Backend и Frontend для отображения и восстановления истории переписки.*

```json
{
  "id": "msg-001",
  "role": "assistant",
  "content": "Как сейчас организован учёт?",
  "created_at": "2026-11-09T12:31:00Z"
}
```

Для `GET .../messages` допускаются дополнительные необязательные поля `action` (`Action | null`) и `products` (`ProductCard[]`) у сохранённых сообщений ассистента, чтобы восстановить рекомендации после обновления страницы. Если это реализовано, Backend обязан хранить или восстанавливать эти поля согласованным образом.

## 4. Public API — Frontend ↔ Business Backend

### 4.1. `POST /api/sessions` — создать новую сессию

**Request:** тело отсутствует.  
**Response:** `201 Created`

```json
{
  "session_id": "session-123",
  "status": "active",
  "created_at": "2026-11-09T12:30:00Z"
}
```

Backend создаёт запись в `sessions` и связывает сессию с защищённым механизмом доступа. Frontend сохраняет идентификатор для следующих запросов.

### 4.2. `POST /api/chat` — отправить сообщение

**Request:**

```json
{
  "session_id": "session-123",
  "request_id": "request-456",
  "message": "У нас сеть из 50 магазинов, хотим снизить расходы на электроэнергию"
}
```

| Поле | Тип | Обязательное | Ограничения |
|---|---|---|---|
| `session_id` | `string` | Да | Существующая доступная сессия |
| `request_id` | `string` | Да | Уникальный для новой отправки в пределах сессии |
| `message` | `string` | Да | Не пустое после удаления пробелов; рекомендуемый лимит — 4000 символов для MVP |

**Response:** `200 OK`

```json
{
  "session_id": "session-123",
  "request_id": "request-456",
  "message": {
    "id": "msg-002",
    "role": "assistant",
    "content": "Как сейчас организован сбор показаний электроэнергии в ваших магазинах?",
    "created_at": "2026-11-09T12:31:00Z"
  },
  "action": "ask_question",
  "products": []
}
```

**Response при рекомендации:**

```json
{
  "session_id": "session-123",
  "request_id": "request-789",
  "message": {
    "id": "msg-004",
    "role": "assistant",
    "content": "Для автоматизации сбора показаний можно рассмотреть облачную АСКУЭ. Совместимость счётчиков нужно уточнить.",
    "created_at": "2026-11-09T12:32:00Z"
  },
  "action": "recommend",
  "products": [
    {
      "id": "cloud_askue",
      "name": "Облачная АСКУЭ",
      "description": "Автоматизированный сбор и обработка показаний приборов учёта."
    }
  ]
}
```

**Алгоритм Backend:**

1. Проверить право доступа к `session_id`, формат запроса и `request_id`.
2. Проверить, нет ли активной обработки этой сессии; обработать дубликат по правилам идемпотентности.
3. Прочитать из БД историю **предыдущих завершённых** сообщений, `customer_profile` и `conversation_summary`.
4. Сохранить входящее сообщение как `pending` с данным `request_id` и завершить транзакцию БД.
5. Вызвать внутренний `POST /v1/chat`, передав загруженную историю и **текущее** сообщение отдельно.
6. Проверить AI-ответ и существование всех `product_ids` в каталоге.
7. В одной короткой транзакции сохранить ответ ассистента, обновлённый профиль и резюме; отметить запрос как `completed`.
8. Вернуть публичный ответ. При сбое пометить запрос как `failed` и не создавать вымышленный ответ ассистента.

**Примечание:** не держать открытую транзакцию БД всё время генерации LLM.

### 4.3. `GET /api/sessions/{session_id}/messages` — история чата

**Request:** только path-параметр `session_id`.  
**Response:** `200 OK`

```json
{
  "session_id": "session-123",
  "messages": [
    {
      "id": "msg-001",
      "role": "user",
      "content": "У нас 50 магазинов",
      "created_at": "2026-11-09T12:30:10Z"
    },
    {
      "id": "msg-002",
      "role": "assistant",
      "content": "Как сейчас собираете показания?",
      "created_at": "2026-11-09T12:30:15Z",
      "action": "ask_question",
      "products": []
    }
  ]
}
```

Для MVP можно возвращать всю историю короткого диалога без пагинации. В более развитой версии стоит предусмотреть `limit` и `cursor`. Доступ — только к собственной сессии.

### 4.4. `POST /api/leads` — создать заявку менеджеру

**Request:**

```json
{
  "session_id": "session-123",
  "submission_id": "submission-001",
  "contact": {
    "name": "Иван",
    "company": "ООО Компания",
    "phone": "+79990000000",
    "email": null
  },
  "consent": true
}
```

- `session_id`: доступная сессия с историей консультации.
- `submission_id`: уникальный ключ отправки заявки для защиты от дублей.
- `contact.name`: обязательная непустая строка.
- `contact.company`: `string | null`.
- `contact.phone`: `string | null`.
- `contact.email`: `string | null`.
- Должен быть указан **хотя бы один** способ связи: телефон или email. Проверяются корректность формата и разумные ограничения длины.
- `consent`: должно быть `true`; факт согласия фиксируется вместе со временем (при необходимости — с версией текста согласия).

Backend берёт `customer_profile`, `conversation_summary` и рекомендованные `product_ids` из сохранённых результатов консультации. Frontend не присылает их как доверенные данные.

**Response:** `201 Created`

```json
{
  "lead_id": "lead-001",
  "status": "new",
  "created_at": "2026-11-09T12:35:00Z"
}
```

Повтор того же `(session_id, submission_id)` возвращает уже созданную заявку без дублирования (рекомендуется `200 OK` с тем же телом). Создание заявки не должно происходить только на основании `action=offer_handoff`: пользователь явно отправляет форму.

### 4.5. `GET /api/admin/leads` — список заявок менеджера

**Request:** только `lead_id` в URL; требуется авторизация менеджера.  
**Response:** `200 OK`

```json

  "session_id": "session-123",
  "status": "new",
  "contact": {
    "name": "Иван",
    "company": "ООО Компания",
    "phone": "+79990000000",
    "email": null
  },
  "customer_profile": {
    "business_type": "retail",

  "created_at": "2026-11-09T12:35:00Z"
}
```

## 5. Internal API — Business Backend ↔ AI Service

### 5.1. `POST /v1/chat` — получить структурированный AI-ответ

**Вызывающая сторона:** только Business Backend.  
**Request:**

```json
{
  "session_id": "session-123",
  "request_id": "request-789",
  "message": "Показания собираем вручную",
  "history": [
    {
      "role": "user",
      "content": "У нас сеть из 50 магазинов, хотим снизить расходы"
    },
    {
      "role": "assistant",
      "content": "Как сейчас организован сбор показаний электроэнергии?"
    }
  ],
  "customer_profile": {
    "business_type": "retail",
    "objects_count": 50,
    "problem": "Высокие расходы на электроэнергию",
    "metering_method": null
  },
  "conversation_summary": null
}
```

| Поле | Тип | Обязательное | Назначение |
|---|---|---|---|
| `session_id` | `string` | Да | Корреляция и диагностика, **не** ключ поиска истории внутри AI |
| `request_id` | `string` | Да | Сопоставление вызова с входным сообщением |
| `message` | `string` | Да | Текущее сообщение пользователя |
| `history` | `HistoryMessage[]` | Да | Предыдущие завершённые сообщения (может быть `[]`) |
| `customer_profile` | `CustomerProfile` | Да | Последний сохранённый профиль |
| `conversation_summary` | `string \| null` | Да | Ранее сформированное резюме или `null` |

**Response:** `200 OK`

```json
{
  "action": "recommend",
  "answer": "Поскольку показания собираются вручную, можно рассмотреть облачную АСКУЭ. Для проверки возможности подключения потребуется уточнить модели счётчиков.",
  "product_ids": ["cloud_askue"],
  "customer_profile": {
    "business_type": "retail",
    "objects_count": 50,
    "problem": "Высокие расходы на электроэнергию",
    "metering_method": "manual"
  },
  "conversation_summary": "Клиент управляет сетью из 50 магазинов, хочет снизить расходы на электроэнергию. Показания собираются вручную. Предварительно рекомендована облачная АСКУЭ, требуется проверить совместимость оборудования."
}
```

Требования к ответу AI:

- `action`: одно значение из `Action`.
- `answer`: непустой текст для пользователя.
- `product_ids`: массив ID из каталога, пустой, если рекомендация не дана.
- `customer_profile`: полный актуальный снимок всех полей (включая `null` для неизвестных данных).
- `conversation_summary`: строка с кратким резюме или `null`, если значимой информации пока нет.
- Для `action = "recommend"` обычно ожидается хотя бы один действительный `product_id`; Backend проверяет это бизнес-правилом.
- Модель не должна создавать цены, гарантии экономии, свойства или продукты, отсутствующие в проверенной базе знаний.
- AI не обращается к БД пользовательских сессий и не создаёт заявки. Контакты через этот эндпоинт не передаются.

**Контекст LLM:** системный промпт и правила → проверенные данные из продуктовой базы / RAG → прежнее резюме и профиль → `history` → текущее `message`. На первом этапе в контекст можно включать полную историю; позднее AI может самостоятельно сокращать её при соблюдении ограничений контекстного окна модели.

### 5.2. `GET /health` — проверка работоспособности

**Реализуется** в Backend и AI Service (на соответствующих внутренних адресах).

**Response:** `200 OK`

```json
{
  "status": "ok"
}
```

Проверка `/health` должна быть лёгкой и не вызывать LLM. Для диагностики внешних зависимостей при необходимости используется отдельная проверка readiness, не обязательная для MVP.

## 6. Единый формат ошибок

Для ошибок рекомендуется совместимый с **RFC 9457 (Problem Details for HTTP APIs)** JSON. Например, при недоступности AI:

**Response:** `503 Service Unavailable` (или `504 Gateway Timeout`, если истекло время ожидания)

```json
{
  "type": "about:blank",
  "title": "Service Unavailable",
  "status": 503,
  "detail": "ИИ-консультант временно недоступен. Повторите попытку позже.",
  "error_code": "AI_SERVICE_UNAVAILABLE"
}
```

| Код | Случай |
|---|---|
| `400` | Нарушение бизнес-правила или некорректное действие |
| `401` | Пользователь не аутентифицирован, когда это требуется |
| `403` | Доступ к сессии / менеджерскому разделу запрещён |
| `404` | Сессия или заявка не найдена |
| `409` | В сессии уже обрабатывается другое сообщение / конфликт состояния |
| `422` | Данные не проходят валидацию схемы |
| `502` | Недопустимый структурированный ответ AI |
| `503` | AI-сервис недоступен |
| `504` | Превышено время ожидания AI-сервиса |

**Важно:** FastAPI по умолчанию возвращает собственный формат для ошибок валидации. Для единого формата потребуется обработчик исключений. Не возвращать пользователю traceback, SQL-ошибки или содержимое секретов.

## 7. Таблицы центральной БД (минимальная логическая модель)

| Таблица | Основные поля | Ответственность |
|---|---|---|
| `sessions` | `id`, `status`, `created_at` | Backend |
| `messages` | `id`, `session_id`, `request_id`, `role`, `content`, `status`, `created_at`, `action`/`product_ids` при необходимости | Backend |
| `customer_profiles` | `session_id`, `business_type`, `objects_count`, `problem`, `metering_method`, `conversation_summary`, `updated_at` | Backend хранит, AI формирует |
| `leads` | `id`, `session_id`, `submission_id`, контакты, снимок профиля, summary, IDs продуктов, `consent_at`, `status` | Backend |

Рекомендуемые ограничения:

- индекс истории сообщений по `(session_id, created_at)`; при необходимости добавить монотонный порядковый номер для строгого порядка;
- уникальность `(session_id, request_id)` на уровне логики обработанных пользовательских запросов;
- уникальность `(session_id, submission_id)` для заявок;
- внешние ключи на `session_id`;
- сохранение **снимка** профиля/резюме в `leads` на момент создания заявки, чтобы она не менялась при последующем диалоге;
- статусы обработки сообщений `pending | completed | failed` и отдельный статус заявки `new` (остальные — по потребностям менеджерского интерфейса).

## 8. Pydantic v2: опорные модели контракта

Ниже — рекомендуемая основа, от которой Backend и AI Service могут создавать собственные модели. На границе HTTP важно совпадение **JSON-схем**, а не импорт классов из одного Python-модуля.

```python
from datetime import datetime
from enum import Enum

from pydantic import BaseModel, Field, model_validator


class Action(str, Enum):
    ANSWER_QUESTION = "answer_question"
    ASK_QUESTION = "ask_question"
    RECOMMEND = "recommend"
    OFFER_HANDOFF = "offer_handoff"
    OUT_OF_SCOPE = "out_of_scope"


class MessageRole(str, Enum):
    USER = "user"
    ASSISTANT = "assistant"


class HistoryMessage(BaseModel):
    role: MessageRole
    content: str = Field(min_length=1)


class CustomerProfile(BaseModel):
    business_type: str | None
    objects_count: int | None = Field(ge=1)
    problem: str | None
    metering_method: str | None


class ProductCard(BaseModel):
    id: str
    name: str
    description: str


class ChatMessage(HistoryMessage):
    id: str
    created_at: datetime


class FrontChatRequest(BaseModel):
    session_id: str
    request_id: str
    message: str = Field(min_length=1, max_length=4000)


class FrontChatResponse(BaseModel):
    session_id: str
    request_id: str
    message: ChatMessage
    action: Action
    products: list[ProductCard]


class AIChatRequest(BaseModel):
    session_id: str
    request_id: str
    message: str = Field(min_length=1, max_length=4000)
    history: list[HistoryMessage]
    customer_profile: CustomerProfile
    conversation_summary: str | None


class AIChatResponse(BaseModel):
    action: Action
    answer: str = Field(min_length=1)
    product_ids: list[str]
    customer_profile: CustomerProfile
    conversation_summary: str | None


class ContactInfo(BaseModel):
    name: str = Field(min_length=1)
    company: str | None = None
    phone: str | None = None
    email: str | None = None

    @model_validator(mode="after")
    def require_contact_method(self):
        if not self.phone and not self.email:
            raise ValueError("Нужен телефон или email")
        return self


class LeadCreateRequest(BaseModel):
    session_id: str
    submission_id: str
    contact: ContactInfo
    consent: bool


class LeadCreateResponse(BaseModel):
    lead_id: str
    status: str
    created_at: datetime
```

**Примечания к схемам:**

1. В Pydantic v2 тип `str | None` **без значения по умолчанию** означает обязательное присутствие ключа при допустимости `null`. Это соответствует полному снимку `CustomerProfile`.
2. `model_validator` выше проверяет наличие контакта, **не формат** телефонного номера/email; окончательная проверка и согласие `consent is True` — на Backend. Для email можно использовать специализированный тип или отдельную проверку.
3. Для `POST /api/sessions`, `GET /api/sessions/{id}/messages` и менеджерских маршрутов создаются дополнительные модели по примерам раздела 4.
4. Публичные `ChatMessage` в истории можно расширить полями `action` и `products`, чтобы корректно восстанавливать интерактивные карточки.
5. Формат LLM Structured Outputs и HTTP-ответ AI Service может быть одной Pydantic-моделью, если требования совместимы; при необходимости разделите внутренний ответ LLM и внешний `AIChatResponse` для дополнительной проверки.

## 9. Проверка интеграции (acceptance checklist)

- [ ] Создание сессии возвращает `session_id`, право доступа к ней проверяется.
- [ ] Первое сообщение передаётся AI с `history: []`.
- [ ] Во втором запросе AI получает оба предыдущих сообщения (`user`, затем `assistant`) и новый `message` отдельно.
- [ ] История восстанавливается из БД после обновления страницы.
- [ ] При `action = "recommend"` Frontend показывает карточку из каталога, а не придуманные LLM характеристики.
- [ ] При `action = "offer_handoff"` форма предлагается, но заявка автоматически не создаётся.
- [ ] Заявка создаётся только по явной отправке формы с согласиями и валидными контактами.
- [ ] Менеджер видит сохранённый снимок заявки с кратким резюме и рекомендацией.
- [ ? ] Повтор с тем же `request_id`/`submission_id` не создаёт дубль.
- [ ] Ошибка AI не теряет входящее сообщение и не создаёт фиктивный ответ.
- [ ? ] Фронтенд, Backend, AI Service и БД запускаются совместно через Docker Compose.

## 10. Открытые решения после получения официального кейса

1. Полный перечень продуктов и официальные `product_ids`.
2. Нужен ли RAG или достаточно структурированного каталога.
3. Требования к каналу передачи заявки (панель менеджера, email, CRM).
4. Поля контактов, текст согласия и правила хранения персональных данных.
5. Нужна ли авторизация менеджера с конкретными ролями.
6. Ограничения на выбор LLM-провайдера, внешний API и передачу данных.
7. Требуются ли показатели качества, ссылки на источники или дополнительные поля `AIChatResponse`.
