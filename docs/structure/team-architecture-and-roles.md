# EnergyTool AI — архитектура проекта и зоны ответственности команды

> **Статус:** предварительный план разработки MVP  
> **Версия:** `1.0-draft` · **Дата:** 7 ноября 2026 года  
> **Период хакатона:** 9–16 ноября 2026 года  
> **Команда:** Frontend Developer · Backend Developer · AI/ML Engineer  
> **Связанный документ:** [`api-contract.md`](./api-contract.md) — подробные структуры HTTP-запросов и ответов.

## 1. Зачем мы создаём проект

Цель — разработать **прототип ИИ-консультанта для сайта EnergyTool**, который помогает посетителю разобраться в продуктах МТС для учёта и экономии энергоресурсов.

Ожидаемый пользовательский сценарий:

1. Посетитель описывает проблему своими словами, например: «У нас сеть магазинов, слишком много времени уходит на сбор показаний».
2. ИИ-консультант уточняет обстоятельства, не повторяя уже заданные вопросы.
3. На основе проверенных сведений о продуктах EnergyTool он предлагает подходящее решение либо честно указывает, каких данных пока недостаточно.
4. При заинтересованности посетителя система предлагает оставить контакты.
5. После согласия пользователя создаётся **структурированная заявка для менеджера** с контактами, проблемой, рекомендацией и кратким резюме консультации.
6. В демонстрационной панели менеджер видит поступившую заявку.

**Ключевая задача:** продемонстрировать работающий путь от первого сообщения клиента до готовой заявки. Мы не разрабатываем систему управления энергосчётчиками, аналитическую платформу энергопотребления или полноценную CRM.

**Важно:** официальное подробное ТЗ на момент составления документа ещё не получено. Все решения ниже являются предварительными и могут корректироваться после публикации кейса и вопросов организаторам.

## 2. Архитектура: как связаны компоненты

```text
                          БРАУЗЕР ПОЛЬЗОВАТЕЛЯ
                     ┌──────────────────────────┐
                     │ Frontend (React / TS)    │
                     │ Чат, рекомендации, формы │
                     │ Панель менеджера         │
                     └────────────┬─────────────┘
                                  │ HTTP / JSON
                                  │ /api/*
                                  ▼
                     ┌──────────────────────────┐
                     │ Business Backend         │
                     │ FastAPI                   │
                     │ Сессии, история, заявки  │
                     │ Валидация и права        │
                     └────────┬─────────┬───────┘
                              │         │ HTTP / JSON
                       SQL/ORM│         │ /v1/chat
                              ▼         ▼
                  ┌────────────────┐  ┌──────────────────────┐
                  │ Central DB     │  │ AI Service           │
                  │ sessions       │  │ FastAPI              │
                  │ messages       │  │ Context Builder      │
                  │ profiles       │  │ Product KB / RAG     │
                  │ leads          │  │ LLM + Structured Out │
                  └────────────────┘  └───────────┬──────────┘
                                                  │
                                                  ▼
                                      ┌──────────────────────┐
                                      │ Внешний LLM API      │
                                      └──────────────────────┘
```

### Принципы архитектуры

- **Frontend** взаимодействует только с публичным API Business Backend. Напрямую к LLM, AI Service и БД он не обращается.
- **Business Backend** — единственный компонент с прямым доступом к пользовательской БД. Он управляет состоянием приложения и созданием заявок.
- **AI Service** — самостоятельный HTTP-сервис, который получает необходимый контекст в запросе, формирует результат и **не хранит историю диалогов пользователей**.
- **Общая БД** — источник истины о сессиях, сообщениях, профилях и заявках. В первом MVP **нет кэша истории**.
- **Каталог продуктов EnergyTool** — отдельные проверенные данные (например, `data/products.json`). При необходимости AI Service использует RAG для поиска по документации. Это не пользовательская БД.
- Для первого MVP используются **обычные HTTP-запросы с JSON**. WebSocket, потоковая генерация, брокеры сообщений и Kubernetes не нужны без дополнительных требований.

Разделение на два серверных приложения выбрано для независимой работы Backend и AI/ML разработчиков. Это не означает, что нужно проектировать сложную микросервисную платформу.

## 3. Обязанности участников

### 3.1. Frontend Developer — интерфейс и пользовательские сценарии

Frontend-разработчик отвечает за всё, что человек видит и с чем взаимодействует в браузере. Его работа не ограничивается внешним видом чата: интерфейс должен надёжно передавать запросы, показывать состояния обработки и не терять доступ к текущему диалогу.

**Что реализуется:**

1. **Страница чата.** Поле ввода, отправка сообщений (в том числе по Enter), отображение сообщений пользователя и ассистента, автопрокрутка, корректная работа с длинными текстами.
2. **HTTP-клиент для Backend.** Запросы создания сессии, отправки сообщений, загрузки истории, создания заявки и получения данных менеджера. Обработка успешных ответов, ошибок и времени ожидания.
3. **Состояние интерфейса.** Пока ответ генерируется, показывается индикатор ожидания. Повторная отправка блокируется или корректно обрабатывается. В случае ошибки пользователь видит понятное сообщение.
4. **Работа с сессией.** После открытия чата вызывается `POST /api/sessions` или используется ранее созданная сессия, если у пользователя сохранился допустимый доступ к ней. После перезагрузки страницы история загружается через Backend. `session_id` сам по себе не является подтверждением права доступа.
5. **Показ рекомендаций.** При `action = "recommend"` рядом с сообщением отображаются карточки продуктов из поля `products`. Frontend не извлекает названия продуктов из произвольного текста LLM.
6. **Форма обратной связи.** При `action = "offer_handoff"` предлагается форма имени, организации, телефона или почты и согласия на обработку данных. Пользователь может не оставлять контакты и продолжить разговор.
7. **Демонстрационная панель менеджера.** Список заявок и страница/модальное окно с деталями: контакт, проблема, потребности, рекомендованный продукт, резюме. Доступ должен быть ограничен.
8. **Удобство демонстрации.** Адаптивность, понятные подписи, обработка пустых состояний, быстрый переход между чат-экраном и панелью менеджера в рамках разрешённого доступа.

**Что не входит в роль Frontend:** выполнение RAG, выбор продуктов, формирование бизнес-профиля через LLM, прямые SQL-запросы, хранение API-ключа модели в браузере.

**Промежуточный результат:** работающий интерфейс на mock-ответах Backend по согласованному JSON-контракту.  
**Готовность:** пользователь может пройти весь сквозной сценарий через реальные API.

### 3.2. Backend Developer — данные, бизнес-операции, интеграция

Backend — центр приложения. Он принимает запросы из браузера, проверяет их, обращается к БД и AI Service, после чего возвращает согласованный ответ. Именно Backend отвечает за то, что консультация становится сохранённой историей и оформленной заявкой.

**Что реализуется:**

1. **Публичный REST API.** Маршруты `/api/sessions`, `/api/chat`, `/api/leads`, `/api/admin/leads` и загрузка истории. Схемы Pydantic и документация OpenAPI.
2. **Управление сессиями.** Создание уникальных идентификаторов, проверка статуса и права доступа, предотвращение доступа к чужой истории.
3. **Единая БД.** Модели `sessions`, `messages`, `customer_profiles`, `leads`; создание таблиц/миграции; методы чтения и записи через ORM или репозитории.
4. **Обработка сообщения.** Получить сообщение, загрузить историю завершённых сообщений и актуальный профиль, зарегистрировать запрос, вызвать AI Service, проверить ответ, сохранить результат, вернуть Frontend.
5. **HTTP-клиент AI Service.** Вызов внутреннего `POST /v1/chat` с тайм-аутом, обработкой недоступности и ошибок формата. В AI Service передаётся полная история предыдущего диалога, а текущее сообщение — отдельным полем `message`.
6. **Заявки.** Проверка контактных данных и согласия; создание записи в `leads` из контактов Frontend плюс сохранённых профиля, резюме и рекомендаций. Факт действия `offer_handoff` сам по себе не создаёт заявку.
7. **API панели менеджера.** Получение списка и подробностей заявок, ограничение доступа.
8. **Надёжность.** Защита от повторных запросов по `request_id`, отсутствие дублей заявок по `submission_id`, обработка одновременных сообщений одной сессии, сохранение состояний `pending/completed/failed`.
9. **Совместный запуск сервисов.** Конфигурация БД, Docker Compose, `.env.example`, проверка `/health`, базовые интеграционные тесты.

**Что не входит в роль Backend:** проектирование промптов, реализация RAG и LLM-клиента, смысловая оценка потребностей пользователя (за исключением технической валидации ответов).

**Промежуточный результат:** Backend с БД и работающими публичными эндпоинтами, где AI Service временно заменён заглушкой.  
**Готовность:** Backend обеспечивает корректное сохранение диалога и заявки даже при перезагрузке приложения и предсказуемо обрабатывает ошибки AI.

### 3.3. AI/ML Engineer — интеллектуальная обработка и рекомендации

AI/ML-разработчик отвечает за отдельный API-сервис, который принимает историю и текущее сообщение, понимает запрос клиента и формирует структурированный результат. AI Service не должен знать внутреннюю схему пользовательской БД и не должен самостоятельно создавать заявки.

**Что реализуется:**

1. **HTTP-интерфейс AI Service.** `POST /v1/chat` с проверкой входной модели и выходным типизированным ответом; `GET /health` для проверки доступности.
2. **Интеграция с LLM.** Настройка клиента модели, системного промпта, контроль ошибок, отказов и допустимого объёма контекста.
3. **Контекст диалога.** Из `history`, текущего `message`, `customer_profile`, `conversation_summary` и знаний о продуктах строится запрос к LLM. При первом MVP можно передавать всю историю; оптимизация контекста — только при необходимости.
4. **Логика консультации.** Модель выбирает одно из действий: `answer_question`, `ask_question`, `recommend`, `offer_handoff`, `out_of_scope`. Это метки ответов, **а не прямые команды изменять БД или отправлять заявку**.
5. **Знания EnergyTool.** Проверенный каталог продуктов, условия применимости, ограничения, допустимые продуктовые ID. RAG добавляется, если объём и характер предоставленных материалов это оправдывают.
6. **Structured Outputs.** Формирование `AIChatResponse`: `action`, `answer`, `product_ids`, обновлённый `customer_profile`, `conversation_summary`. Нужна проверка фактической допустимости `product_ids`, не только соответствия JSON-схеме.
7. **Извлечение профиля клиента.** Сбор известных фактов: тип бизнеса, количество объектов, проблема, способ учёта. При новых сообщениях уже подтверждённые сведения сохраняются, исправления пользователя учитываются, противоречия уточняются.
8. **Резюмирование консультации.** Короткое содержательное резюме, которое менеджер получит при создании заявки.
9. **Проверка качества.** Набор тестовых диалогов, негативные сценарии, проверка отсутствия придуманных продуктов и необоснованных обещаний цены или экономии.

**Что не входит в роль AI/ML:** прямой доступ к пользовательским таблицам, сохранение сессий, оформление контактов и финальная отправка заявок, реализация браузерного интерфейса.

**Промежуточный результат:** `POST /v1/chat` принимает вручную подготовленный контекст и возвращает корректный типизированный JSON.  
**Готовность:** AI выдаёт обоснованные рекомендации по проверенным сведениям и корректно ведёт многошаговый диалог.

### 3.4. Задачи, которые нельзя полностью закрепить за одним участником

- **API-контракт и изменение схем** обсуждаются втроём; изменения фиксируются в `docs/api-contract.md` до интеграции.
- **Каталог продуктов** должен быть фактически проверен; AI/ML отвечает за применение в рекомендациях, Backend — за сопоставление `product_ids` с публичными карточками, Frontend — за отображение.
- **Интеграционные тесты** проводятся совместно на одном наборе тестовых сценариев.
- **Презентация и демонстрация** — общая ответственность. Каждый участник должен уметь объяснить свой компонент и общий поток данных.
- **Решения о сокращении объёма MVP** принимаются совместно с капитаном после оценки рисков для сквозного сценария.

## 4. Сценарии взаимодействия сервисов

### 4.1. Создание сессии и восстановление истории

```text
Пользователь открывает чат
    Frontend → POST /api/sessions → Backend
    Backend → INSERT sessions → DB
    Backend → session_id → Frontend

После перезагрузки страницы (при сохранённом праве доступа):
    Frontend → GET /api/sessions/{id}/messages → Backend
    Backend → SELECT messages → DB
    Backend → messages[] → Frontend
```

Frontend может хранить идентификатор сессии для удобства, но Backend дополнительно проверяет авторизованный доступ к ней (например, через защищённую серверную cookie).

### 4.2. Обработка сообщения — главный сценарий

```text
1. Frontend → Backend
   POST /api/chat
   {session_id, request_id, message}

2. Backend → DB
   Проверка доступа, загрузка предыдущей истории и профиля.
   Сохранение текущего запроса со статусом pending.

3. Backend → AI Service
   POST /v1/chat
   {session_id, request_id, message, history,
    customer_profile, conversation_summary}

4. AI Service → LLM
   System Prompt + данные каталога/RAG + профиль + история
   + текущее сообщение → структурированный AIResponse.

5. AI Service → Backend
   {action, answer, product_ids,
    customer_profile, conversation_summary}

6. Backend → DB
   Валидация и сохранение ответа, профиля и резюме;
   статус запроса completed.

7. Backend → Frontend
   {session_id, request_id, message, action, products}
```

**Важные договорённости:**

- `history` содержит только **предыдущие завершённые** сообщения по порядку. Текущий `message` не дублируется в истории.
- Backend читает историю из БД **при каждом запросе**. Кэширование сознательно исключено из MVP.
- AI Service не пишет в БД пользовательских диалогов и не имеет собственного хранилища пользовательских сессий.
- Backend валидирует ответ AI и сверяет `product_ids` с утверждённым каталогом.
- Для долгого вызова LLM не следует держать открытую транзакцию БД. При ошибке запрос отмечается как `failed`, а пользователю возвращается согласованная ошибка.

### 4.3. Рекомендация продукта

После получения `action = "recommend"` и проверенных `product_ids` Backend собирает карточки из каталога и возвращает их в `products`. Frontend показывает текст ответа и карточки решений. Названия, характеристики и обещания экономии не должны генерироваться произвольно.

### 4.4. Создание заявки

```text
AI: action = offer_handoff
    ↓
Frontend предлагает контактную форму
    ↓
Пользователь подтверждает отправку и согласие
    ↓
Frontend → POST /api/leads → Backend
    ↓
Backend проверяет контактные данные, сессию, согласие
    ↓
Backend объединяет контакты с сохранённым профилем,
резюме диалога и рекомендацией → INSERT leads
    ↓
Frontend получает lead_id и подтверждение
    ↓
Менеджер видит заявку через GET /api/admin/leads
```

Заявка не создаётся автоматически из-за одного лишь действия модели. В MVP **передача менеджеру** может быть реализована как появление записи в защищённой демонстрационной панели. Если официальное ТЗ потребует CRM, почтовую доставку или другой способ передачи, реализацию нужно пересмотреть.

## 5. Краткая карта API

Подробные структуры, типы, ограничения полей, JSON-примеры и коды ошибок находятся в [`api-contract.md`](./api-contract.md). Не стоит поддерживать две расходящиеся версии одного контракта.

### Public API: Frontend → Backend

| Метод | Маршрут | Для чего нужен |
|---|---|---|
| `POST` | `/api/sessions` | Создать новую сессию |
| `GET` | `/api/sessions/{session_id}/messages` | Загрузить историю |
| `POST` | `/api/chat` | Отправить сообщение консультанту |
| `POST` | `/api/leads` | Создать заявку после подтверждения |
| `GET` | `/api/admin/leads` | Список заявок для менеджера |
| `GET` | `/api/admin/leads/{lead_id}` | Подробности заявки |

### Internal API: Backend → AI Service

| Метод | Маршрут | Для чего нужен |
|---|---|---|
| `POST` | `/v1/chat` | Получить структурированный ответ AI |
| `GET` | `/health` | Лёгкая проверка доступности AI Service |

В Backend также нужен собственный `GET /health`.

### Пример внутреннего запроса и ответа

Запрос к AI Service:

```json
{
  "session_id": "session-123",
  "request_id": "request-456",
  "message": "Показания собираем вручную",
  "history": [
    {"role": "user", "content": "У нас 50 магазинов"},
    {"role": "assistant", "content": "Как сейчас собираете показания?"}
  ],
  "customer_profile": {
    "business_type": "retail",
    "objects_count": 50,
    "problem": "Высокие расходы на электроэнергию",
    "metering_method": null
  },
  "conversation_summary": null
}
```

Ответ AI Service:

```json
{
  "action": "recommend",
  "answer": "Для автоматизации сбора показаний можно рассмотреть облачную АСКУЭ. Совместимость оборудования нужно уточнить.",
  "product_ids": ["cloud_askue"],
  "customer_profile": {
    "business_type": "retail",
    "objects_count": 50,
    "problem": "Высокие расходы на электроэнергию",
    "metering_method": "manual"
  },
  "conversation_summary": "Сеть из 50 магазинов; показания собираются вручную. Клиент заинтересован в автоматизации учёта."
}
```

Идентификаторы продуктов и сведения в примере **условные**; фактические должны сверяться с продуктовым каталогом.

### Общие справочные типы

- **`Action`** — выбранный моделью вид следующего диалогового действия.
- **`HistoryMessage`** — сообщение (`role`, `content`) для истории, передаваемой в AI Service.
- **`CustomerProfile`** — структурированная память о потребностях клиента, которую AI обновляет, а Backend сохраняет.
- **`ProductCard`** — проверенная карточка продукта для отображения во Frontend.
- **`ChatMessage`** — сохранённое сообщение с идентификатором и временной меткой для пользовательского интерфейса.

**Согласование профиля:** текущая версия `api-contract.md` содержит четыре поля `CustomerProfile` (`business_type`, `objects_count`, `problem`, `metering_method`). Возможное расширение (`goal`, `resource_types`, `existing_system`, `equipment_info`) обсуждается отдельно. При утверждении расширения одновременно обновляются API-контракт, Pydantic-схемы, тесты и модель хранения.

## 6. Хранение данных

Для MVP достаточно **одной реляционной БД**. Это не запрещает выделить несколько логических репозиториев в коде Backend.

| Сущность | Что хранится |
|---|---|
| `sessions` | ID, состояние сессии, даты создания/обновления |
| `messages` | ID, сессия, роль, текст, порядок, статус, связанный `request_id` |
| `customer_profiles` | Последний проверенный профиль и краткое резюме |
| `leads` | Контакты, профиль и рекомендация на момент заявки, статус, дата согласия |

Для получения истории нужен индекс по `session_id` и порядку сообщений. Backend должен различать сообщения, уже завершённые ответом, и сообщения с незавершённой/ошибочной обработкой.

**Пользовательские данные не нужно дублировать в AI Service.** История извлекается из центральной БД перед каждым обращением к модели. Каталог продуктов и поисковый индекс RAG не являются хранилищем клиентских диалогов и могут располагаться в AI-компоненте.

## 8. Совместная разработка и интеграция

### Контракт сначала, реализация потом

**До разработки каждого интеграционного узла** команда согласует путь, структуру JSON, обязательные поля и ожидаемые ошибки. Затем компоненты можно разрабатывать независимо:

- Frontend использует mock-ответы `/api/chat`.
- Backend использует mock-ответы `/v1/chat`.
- AI/ML проверяет свой `/v1/chat` вручную подготовленными историями диалогов.

Изменения API обсуждаются со сторонами, которых они затрагивают. Если меняется поле `customer_profile`, необходимо синхронно обновить тесты и модели как минимум Backend и AI Service.

### Git и договорённости команды

- Рабочие ветки: `feature/frontend-chat`, `feature/backend-sessions`, `feature/ai-chat` (названия примерные).
- Небольшие коммиты с описанием результата; изменения объединяются через Pull Request или согласованный процесс ревью.
- Главная ветка должна оставаться запускаемой; перед слиянием проверяются хотя бы базовые тесты и локальный запуск.
- Секреты не коммитятся. В `.env.example` указываются только **имена** переменных без реальных значений ключей.
- Каждый день — короткая синхронизация: что готово, какой блокер, что меняется в контракте, что нужно другому участнику.

### Минимальное тестирование

Проверять стоит не только положительный сценарий, но и:

1. Пользователь даёт неполное описание проблемы → AI задаёт уместный вопрос.
2. Пользователь исправляет ранее названное число объектов → профиль меняется корректно.
3. В базе знаний нет подтверждения характеристики → AI не придумывает факт.
4. Пользователь отказывается оставлять контакты → чат продолжается, заявка не создаётся.
5. LLM недоступна → показывается ошибка, история не повреждается.
6. Один и тот же `request_id` отправлен повторно → дублирования сообщения/вызова LLM нет.
7. Пользователь обновляет страницу → история восстанавливается.
8. Пользователь пытается получить чужую историю или менеджерские данные без доступа → запрос отклонён.
9. Заявка действительно содержит актуальные контакты, резюме и рекомендацию.

### MVP: обязательно и необязательно

**Обязательно для предлагаемого MVP:**

- Чат с корректными запросами и ответами.
- Сессии и восстановление истории.
- LLM с контекстом диалога и структурированным ответом.
- Подбор из проверенного каталога EnergyTool.
- Контактная форма и сохранение содержательной заявки.
- Панель менеджера.
- Запуск всей системы, базовая диагностика ошибок, тесты сквозного сценария.

**Можно отложить, если ТЗ не требует:**

- Кэширование истории, Redis, Kafka, WebSocket, streaming.
- Обучение или дообучение собственной LLM.
- Сложный агентный фреймворк или многоагентная система.
- Kubernetes, высокая нагрузка и развитая инфраструктура мониторинга.
- Реальная интеграция с CRM/почтой МТС без доступа и требований.
- Большая дизайн-система, личные кабинеты и сложные анимации.
- Полноценный RAG, если базовый каталог продуктов решает задачу лучше и проще.

## 10. Критерии готовности проекта

Проект можно считать готовым к демонстрации, если **из чистого запуска** команда способна показать следующее:

- [ ] Все компоненты запускаются по README и конфигурации окружения.
- [ ] Посетитель открывает чат и создаёт сессию.
- [ ] Его сообщение доходит до AI, а ответ возвращается через Backend.
- [ ] Во втором и следующих запросах модель получает прежнюю историю диалога.
- [ ] Модель задаёт уточнения и при подходящих данных даёт обоснованную рекомендацию.
- [ ] Нельзя получить несуществующий продукт из `product_ids` без обработки ошибки.
- [ ] История и профиль сохраняются в БД и восстанавливаются после обновления страницы.
- [ ] Пользователь может добровольно оставить контакты; заявка сохраняется один раз.
- [ ] Менеджер видит контакты, потребность, рекомендацию и резюме в защищённой панели.
- [ ] При недоступности AI приложение сообщает об ошибке без потери пользовательских данных.
- [ ] Подготовлены несколько заранее проверенных бизнес-сценариев для демонстрации.

## 11. Базовая безопасность и эксплуатационные ограничения

Это учебный MVP, но несколько требований нельзя откладывать:

- API-ключ LLM находится **только на сервере** и не попадает в JavaScript-пакет Frontend, ответы API или Git.
- Backend проверяет права доступа к сессиям и к панели менеджера. `session_id` не является паролем.
- Контакты собираются после согласия пользователя и не выводятся в открытых логах; для демонстраций используются вымышленные данные.
- Запросы к БД выполняются через ограниченные методы Backend. Не создаётся публичный универсальный endpoint, принимающий произвольные SQL-запросы.
- У AI нет произвольного доступа к контактам клиентов, а содержимое сообщений и RAG-документов рассматривается как недоверенный ввод.
- Продуктовые рекомендации и заявленные свойства должны опираться на проверенные данные. Модель не должна обещать неподтверждённую экономию или цену.
- Ошибки внешних сервисов, тайм-ауты и повторные запросы обрабатываются явно.

Эти меры не заменяют полноценный аудит безопасности, но обеспечивают минимально ответственное поведение прототипа.

## Итоговые договорённости

- **Frontend** отвечает за пользовательский опыт и отображение результатов.
- **Backend** отвечает за данные, сессии, заявки, доступ и связь между компонентами.
- **AI/ML** отвечает за обработку диалога, знания о продуктах, LLM и структурированный результат.
- **Полная история** хранится в общей БД; Backend загружает её при каждом запросе к AI. **Кэш истории не нужен** в первой версии.
- **Изменения в API** сначала отражаются в `docs/api-contract.md`, затем синхронно внедряются затронутыми участниками.
- **Приоритет № 1** — к середине недели получить стабильный сквозной сценарий. Дополнительные возможности добавляются после этого.

*Документ предназначен для предварительного согласования командой. При изменении официального ТЗ, продуктового каталога или API-контракта его следует актуализировать.*
