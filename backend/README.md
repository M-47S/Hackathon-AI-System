# Backend

Основной серверный модуль системы **EnergyTool AI**. Выполняет роль центрального оркестратора, шлюза аутентификации и хранилища состояния диалогов.

## Назначение и архитектура модуля

Бэкенд-сервис спроектирован на языке Go и отвечает за следующие задачи:

1. **Управление доступом и сессиями:** Регистрация и аутентификация пользователей (хэширование паролей через `bcrypt`), генерация и валидация сессионных `HttpOnly` cookies с контролем срока жизни (`ExpiresAt`) в базе данных.
2. **Оркестрация диалога:** Прием сообщений от клиентского интерфейса, загрузка истории переписки из БД, отправка контекста во внутренний Python AI-сервис (`/v1/chat`) по HTTP (клиент `Resty`), сохранение ответов ассистента и обновление структурированного профиля клиента (`Profiles`) и резюме диалога (`ConversationSummary`).
3. **Работа с заявками (Leads):** Валидация контактных данных, сохранение лидов с привязкой массивов рекомендованных продуктов (`text[]`) и предоставление данных для панели менеджера через оптимизированные `LEFT JOIN` выборки.
4. **Слой хранения (PostgreSQL + GORM):** Автоматическая миграция схемы БД (`AutoMigrate`), управление пулом соединений (`SetMaxOpenConns`, `SetMaxIdleConns`) и обеспечение целостности данных через каскадное удаление (`OnDelete:CASCADE`).

### Схема БД (таблицы и связи)

* `customers` (1) ➔ (N) `cookies` (сессионные токены и время их истечения)
* `customers` (1) ➔ (N) `sessions` (диалоговые сессии и `conversation_summary`)
* `sessions` (1) ➔ (N) `messages` (история сообщений и массивы рекомендованных продуктов `rec_products`)
* `sessions` (1) ➔ (1) `profiles` (извлеченные с помощью ИИ параметры бизнеса клиента)
* `sessions` (1) ➔ (N) `leads` (оформленные заявки для менеджеров)

### Структура директории `backend/`

```text
backend/
├── Dockerfile           # Сборка образа
├── docker-compose.yml   # Запуск контейнеров PostgreSQL 16 и Go-сервера
├── go.mod               # Зависимости Go-модуля
├── go.sum           
├── main.go              # Точка входа, инициализация БД, AI-клиента и запуск сервера
├── routes.go            # Настройка CORS, групп маршрутов и Cookie-middleware
├── handlers.go          # HTTP-обработчики эндпоинтов и валидация входящих JSON
├── functions.go         # Бизнес-логика, Generic-репозитории GORM и запросы к AI
├── tables.go            # Модели таблиц PostgreSQL
└── models.go            # DTO-структуры для контрактов API
```

## Запуск Backend-модуля через Docker

Для изолированного запуска Go-сервера и базы данных PostgreSQL из директории `backend/`:

1. Создайте файл `.env` на основе `.env.example`:
   ```bash
   cp .env.example .env
   ```
2. Соберите и запустите контейнеры одной командой:
   ```bash
   docker compose up -d --build
   ```

Остановка и удаление контейнеров:

```bash
docker compose down
```

## Порты и зависимости

### Используемые порты

* **`8080`** — внешний и внутренний порт HTTP-сервера Go (Gin API).
* **`5432`** (или **`5433`** при пробросе на хост) — порт реляционной базы данных PostgreSQL 16.
* **`8001`** (исходящий) — порт подключения к Python AI-сервису.

### Зависимости

* **Компилятор:** Go `1.26+`
* **Веб-фреймворк и CORS:** `github.com/gin-gonic/gin`, `github.com/gin-contrib/cors`
* **ORM и драйвер БД:** `gorm.io/gorm`, `gorm.io/driver/postgres`, `github.com/lib/pq` (работа с массивами `text[]`)
* **HTTP-клиент:** `github.com/go-resty/resty/v2`
* **Безопасность и утилиты:** `golang.org/x/crypto/bcrypt`, `://github.com`, `://github.com`

## Переменные окружения и внешние сервисы

### Подключение к AI-сервису

* **Сервис:** Внутренний Python AI-сервис (FastAPI).
* **Переменная окружения:** `AI_SERVICE_URL`
* **Порядок подключения:** Указывается базовый URL сервиса в `.env` (например, `http://localhost:8001` при локальном запуске, `http://docker.internal` если AI запущен на хосте вне Docker, или `http://ai-service:8001` при работе в общей сети Docker Compose). Авторизация между Go и AI-сервисом работает по внутренней сети без внешнего API-ключа.

### Шаблон переменных `.env.example`

```env
#Настройки пула подключений
DB_MAX_OPEN_CONNS=50
DB_MAX_IDLE_CONNS=10
#Сложность алгоритма хэширования

#Подключение к ДБ

DB_NAME=mts

DB_PORT=5432
DATABASE_URL=host=${DB_HOST} user=${DB_USER} password=${DB_PASSWORD} dbname=${DB_NAME} port=${DB_PORT} sslmode=disable
```

## Краткое описание end-points

Все маршруты имеют базовый префикс `/api`. Защищенная группа требует наличия валидной сессионной cookie (проверяется через `ReadCookieMiddleWare`).

### Публичные маршруты

* **`GET /api/health`** — проверка работоспособности сервера и соединения с базой данных (Healthcheck).
* **`POST /api/register`** — регистрация нового пользователя, хэширование пароля (`bcrypt`), создание записи в `customers` и установка сессионной cookie.
* **`POST /api/login/manual`** — ручная аутентификация по логину и паролю с генерацией новой cookie.
* **`POST /api/logout`** — выход из системы: удаление текущей cookie из базы данных и её очистка в браузере пользователя.

### Защищенные маршруты (требуют Cookie)

#### Сессии и диалог

* **`GET /api/login/cookie`** — автоматическая проверка активности текущей cookie по `ExpiresAt` в БД и восстановление сессии пользователя.
* **`POST /api/sessions`** — создание новой диалоговой сессии (`session_id`) с привязкой к текущему пользователю.
* **`DELETE /api/delete/:session_id`** — удаление выбранной сессии; благодаря `OnDelete:CASCADE` база данных автоматически удаляет связанные с ней сообщения, профиль и заявки.
* **`GET /api/sessions/:session_id/messages`** — получение истории сообщений конкретной сессии с развертыванием идентификаторов рекомендованных продуктов в полные карточки.
* **`POST /api/chat`** — отправка сообщения пользователя, передача истории в Python AI-сервис (`/v1/chat`), сохранение ответа ассистента и обновление профиля клиента (`profiles`) и резюме диалога (`conversation_summary`).

#### Заявки и панель менеджера

* **`POST /api/leads`** — оформление новой заявки с контактными данными клиента и привязкой рекомендованных продуктов.
* **`GET /api/admin/leads`** — получение списка всех заявок для менеджера с объединением данных из таблицы `profiles` (`LEFT JOIN`).
* **`GET /api/admin/leads/:lead_id`** — получение детальной карточки конкретной заявки, контактов клиента, собранного профиля бизнеса и краткого резюме диалога.

## Известные ограничения модуля

* **Разграничение прав доступа:** Проверка прав менеджера для эндпоинтов `/api/admin/*` на уровне MVP опирается на флаг `is_admin` в таблице `customers` без сложной ролевой модели (RBAC).
* **Справочник продуктов:** Маппинг идентификаторов рекомендованных продуктов (`recommended_product_ids`) в полные карточки (`ProductData`) выполняется на стороне Go-бэкенда из встроенного каталога в памяти.
* **Транспортный уровень:** Настройки CORS (`AllowOrigins` из `FRONT_URL`) и флаги `SetCookie` (`Secure: false`) сконфигурированы для локального HTTP-окружения; для продакшена требуется включение `Secure: true` и терминация TLS на уровне балансировщика.

## Дальнейшее развитие и оптимизация

При переходе от MVP к высоким промышленным нагрузкам модуль может быть масштабирован по следующим направлениям:

* **Оптимизация слоя работы с БД:** Замена GORM на нативный драйвер **`pgx/v5`** (`pgxpool`) в связке с кодогенерацией **`sqlc`** или легкой оберткой **`sqlx`**. Это позволит исключить накладные расходы на рефлексию в рантайме, использовать бинарный протокол PostgreSQL и пакетную отправку запросов, кратно снизив задержки и аллокации памяти при чтении/записи. Это позволит ускорить работу с БД, но потребует больших усилий для написания кода с помощью другой библиотеки.
* **Перевод межсервисного взаимодействия на gRPC:** Замена внутренних REST/JSON-запросов между Go-бэкендом и Python AI-сервисом (`/v1/chat`) на **gRPC (HTTP/2 + Protobuf)**. Бинарная сериализация сократит объем передаваемого по сети трафика, уменьшит задержки при передаче длинной истории диалога и обеспечит строгую типизацию контрактов на уровне `.proto`-файлов, а также позволит реализовать потоковую передачу ответов (gRPC Streaming) по мере генерации текста нейросетью.
* **Асинхронная очередь задач и кэширование:** Вынос фоновых операций (обновление `conversation_summary` и профилей) в брокер сообщений для мгновенного возврата ответа пользователю и кэширование активных сессий в Redis для разгрузки PostgreSQL.
